# 审核整改设计：对比度、状态栏、分层图标与边界反馈

## 背景与目标

本轮仅修复审核明确指出的四类问题，不改变页面信息架构、路由、业务数据、LED 展示模式、包名、版本或签名配置。目标设备保持 phone、tablet 和 2in1。

验收标准：

- 图标或标题文字与背景对比度大于 3:1。
- 正文与背景对比度大于 4.5:1。
- 常规页面背景连续覆盖状态栏区域，状态栏信息在深色背景上使用浅色显示。
- LED 全屏展示页继续隐藏系统栏，退出后恢复常规页面系统栏。
- 应用图标由 1024x1024 前景 PNG、1024x1024 背景 PNG 和分层资源描述组成；资源不预裁圆角，主体不额外缩进。
- 所有纵向或横向滚动容器在到达边界时提供弹性反馈。

## 方案比较

### 方案 A：共享契约与最小页面改动（采用）

在 `AppTheme` 集中定义高对比度前景色和合规弱化文字色，通过脚本计算关键前景/背景组合；页面仅替换违规颜色。系统栏仍由 `ScreenService` 统一管理。滚动容器统一显式声明弹性边界效果。图标清单继续使用同一资源名，但该资源改为分层 JSON。

优点是覆盖面可验证、页面改动小、视觉延续性强；代价是需要增强现有静态契约脚本。

### 方案 B：逐页面独立修补

直接修改每个页面中的颜色和滚动属性。初次改动较快，但容易产生颜色漂移和漏项，后续审核难以证明全局一致性，因此不采用。

### 方案 C：整体压暗亮色控件

保留白色按钮文字，通过压暗青色、蓝色、绿色和红色背景满足对比度。该方案会显著削弱现有 LED 霓虹视觉，因此不采用。

## 颜色与组件设计

- 新增 `ON_ACCENT` 深色前景，供亮青、亮蓝、成功和危险按钮文字/图标使用。候选值 `#00131A` 在现有最弱亮色背景上的对比度仍大于 5.5:1。
- 将 `TEXT_MUTED` 从 `#66738A` 提升至 `#8793A8`。它在 `PAGE_BG` 上约为 6.39:1，在 `SURFACE_RAISED` 上约为 5.56:1。
- `TEXT_PRIMARY` 和 `TEXT_SECONDARY` 保持不变；两者在现有深色页面和表面上已满足正文阈值。
- 用户自定义 LED 字幕颜色属于内容创作能力，不强制改写；应用自身固定 UI 文本、按钮标签和图标必须使用合规主题色。
- 禁用态保留可辨识反馈，但不将低透明度作为正常可读正文样式。

## 状态栏设计

- 常规页面继续使用全屏布局，并让统一的 `PAGE_BG` 延伸到状态栏和导航栏安全区域，避免顶部形成独立色带。
- `ScreenService.applyAppChrome()` 统一显示系统栏，设置透明状态栏背景、与页面一致的导航栏背景，以及浅色状态栏/导航栏内容。
- 常规页面根节点保持纯色全宽背景，状态栏区域不使用左右分区或横向渐变。
- 页面内容继续通过安全区内边距避让状态栏；沉浸只延伸背景，不让标题和控件进入系统信息区域。
- `DisplayPage` 继续在进入时隐藏系统栏，离开时调用统一恢复逻辑。

## 分层图标设计

- `AppScope/resources/base/media/app_icon.json` 作为应用图标分层资源，引用 `app_icon_background.png` 和 `app_icon_foreground.png`。
- Ability 图标使用同样结构的 `entry/src/main/resources/base/media/startIcon.json`，引用该模块内的前景/背景资源。
- 两层 PNG 均为 1024x1024。背景层覆盖完整画布；前景层使用透明背景，LED 设备/字幕主体延伸到规范画布范围，不自行绘制最终圆角蒙版，也不添加用于模拟系统裁切的内边距。
- 视觉继续使用深色背景、青蓝 LED 点阵和 `LED` 主体，确保与现有应用识别一致。
- 静态资源测试验证精确尺寸、前景透明像素、背景四角不透明、分层 JSON 引用和清单资源名。

## 边界反馈设计

- `Index` 和 `ColorPickerPage` 的纵向 `Scroll` 启用 `EdgeEffect.Spring`。
- `TemplatePage` 的横向分类 `Scroll` 和纵向模板 `Grid` 启用 `EdgeEffect.Spring`。
- `HistoryPage` 的记录 `List` 启用 `EdgeEffect.Spring`。
- 对可能短于视口的内容使用 `alwaysEnabled: true`，保证用户在顶部、底部、左侧或右侧边界拖动时仍能获得反馈。
- 首页仅作为二维选项排布且自身不承担滚动的内部 `Grid` 不额外启用边界效果，避免嵌套手势冲突。

## 测试与验证

先扩展或新增失败的静态契约，再实施对应改动：

1. 对比度契约计算共享主题和亮色控件组合，旧值应失败，新值应通过。
2. 窗口契约要求透明沉浸状态栏、浅色系统信息和统一深色根背景。
3. 图标契约要求分层 JSON、两层精确 1024x1024、透明前景和不透明满幅背景。
4. UI 契约要求所有实际滚动容器显式启用弹性边界反馈。
5. 执行 `scripts/check-standard.ps1` 和 `scripts/build-harmony.ps1`。
6. 在可用设备上安装启动，检查状态栏连续性、文字可读性、边界回弹和启动器图标；保存不含敏感信息的截图或说明。

## 风险与边界

- 分层资源语法以本机 HarmonyOS SDK/DevEco 预览工程的 `layered-image` 结构为准，并通过真实构建验证。
- 设备启动器会执行自己的图标蒙版；源资源本身不预裁圆角。
- 没有可用 tablet/2in1 时，只能对其做响应式静态与构建验证，设备缺口必须在 `design-qa.md` 如实记录。
